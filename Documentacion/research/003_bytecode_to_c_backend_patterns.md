## 1. Nim (Primary C Backend)

Nim is the **gold standard** for AST-to-C code generation. The compiler generates
human-readable C as its primary compilation target.

### Architecture

```
Source → Lexer → Parser → AST → Semantic Analysis → Transformed AST → C Code → cc → Binary
```

Key source files in the Nim compiler:
- `compiler/cgen.nim` — Main C code generator, orchestrates per-module/per-proc state
- `compiler/ccgexprs.nim` — Generates C expressions from AST nodes
- `compiler/ccgstmts.nim` — Generates C statements (control flow, assignments)
- `compiler/ccgtypes.nim` — Maps Nim types to C type declarations
- `compiler/ccgcalls.nim` — Generates C function calls
- `compiler/cgendata.nim` — Data structures for code generation state

### Core Algorithm: AST-to-C Translation

Nim does **not** go through bytecode. It translates the typed AST directly into
C source text using a "ropes" data structure (a tree of strings for lazy
concatenation).

**Expression Generation** (`ccgexprs.nim`):
Each AST node kind dispatches to a specific C generation function. The `expr()`
function is the main entry point:

```nim
proc expr(p: BProc, n: PNode, d: var TLoc) =
  case n.kind
  of nkIntLit:     genLiteral(p, n, d)
  of nkStrLit:     genStringLiteral(p, n, d)
  of nkCall:       genCall(p, n, d)
  of nkInfix:      genInfixExpr(p, n, d)
  of nkPrefix:     genPrefixExpr(p, n, d)
  of nkDotExpr:    genRecordField(p, n, d)
  of nkBracketExpr: genArrayElem(p, n, d)
  # ... ~200 more cases
```

**Statement Generation** (`ccgstmts.nim`):
Statements are generated by walking the AST and emitting C statements directly:

```nim
# Nim: if x > 0 { echo "positive" }
# Generates C:
# if ((*x) > 0) { echo__sd9aAb23u9bPSe9c2hbSPQxA("positive"); }
```

### Type Mapping

Nim types map to C types via `ccgtypes.nim`:

| Nim Type | C Type |
|----------|--------|
| `int` | `NI` (platform-sized int, typically `long`) |
| `int32` | `NI32` (fixed-width) |
| `float64` | `NF` (typically `double`) |
| `string` | `NimStringV2` (struct with `len` + `p`) |
| `seq[T]` | `NimSeqV2` (struct with `len` + `p`) |
| `object` | C `struct` (with mangled name) |
| `ref T` | `tyObject_*` pointer |
| `enum` | `NI` (backed by int) |
| `bool` | `NIM_BOOL` (`unsigned char`) |
| `ptr T` | `T*` |
| `proc` | Function pointer type |

Generated type declarations look like:
```c
struct tyObject_Foo__abc123 {
  NI x;
  NimStringV2 name;
  NF score;
};
```

### Control Flow

Nim's control flow maps directly to C's:

| Nim | C |
|-----|---|
| `if cond: stmts` | `if (cond) { stmts }` |
| `while cond: stmts` | `while (cond) { stmts }` |
| `for i in 0..n: stmts` | `for (NI i = 0; i <= n; i++) { stmts }` |
| `case x of ...` | `switch (x) { ... }` or `if-else` chain |
| `block: stmts` | `{ stmts }` (scoped block) |
| `break` | `break;` |
| `continue` | `goto Lcontinue;` (with label) |

The compiler transforms `for` loops into `while` loops at the AST level before
C generation. Pattern matching (`case`) generates either `switch` (for enums/integers)
or `if-else` chains (for complex patterns).

### Memory Management

Nim supports multiple GC strategies, all implemented as C runtime calls:

```c
// ARC/ORC (default in modern Nim)
nim IncRef(obj);    // reference counting
nim DecRef(obj);    // decrement + potential destroy
nim Destroy(obj);   // explicit destructor call

// Legacy GC
nimGCvisit(obj);    // mark phase
```

Memory is allocated via:
```c
// Objects on stack (no allocation needed)
tyObject_Foo local_foo;

// Objects on heap (ref types)
tyObject_Foo* obj = (tyObject_Foo*) nimNewObj(sizeof(tyObject_Foo), desc);
```

### Function Calls

```nim
# Nim: proc add(a, b: int): int = a + b
# Generated C:
static N_INLINE NI add__xxx(NI a, NI b) {
  NI result;
  result = (NI)0;
  result = (NI)(a + b);
  return result;
}
```

For closures, Nim generates an environment struct:
```c
struct tyClosure__abc {
  NI env_clP_0;       // captured variable
  NI env_clEnv_0;     // environment pointer
};
```

### Key Pattern: Rope-Based Output

Nim uses a "ropes" data structure — a binary tree of strings — so that string
concatenation is O(log n) instead of O(n). The final C source is built by
flattening the rope. This allows efficient generation without repeated
`memcpy`/`realloc`.

## 2. V / Vlang (Primary C Backend)

V compiles to human-readable C as its primary backend. The approach is very
similar to Nim's but with a different internal architecture.

### Architecture

```
Source → Scanner → Parser → AST → Checker → Typed AST → C Code → cc → Binary
```

Key source files:
- `vlib/v/gen/c/cgen.v` — Main code generator
- `vlib/v/gen/c/fn.v` — Function generation
- `vlib/v/gen/c/for.v` — For-loop generation
- `vlib/v/gen/c/if.v` — If-statement generation
- `vlib/v/gen/c/array.v` — Array type generation
- `vlib/v/gen/c/str.v` — String generation
- `vlib/v/gen/c/struct.v` — Struct generation
- `vlib/v/gen/c/assign.v` — Assignment generation

### Core Algorithm

V uses a `Gen` struct with **multiple string builders** to generate code into
separate sections that are assembled in the correct order:

```v
struct Gen {
  out             strings.Builder   // main function bodies
  cheaders        strings.Builder   // #include, #define
  typedefs        strings.Builder   // typedef, struct declarations
  definitions     strings.Builder   // top-level definitions
  auto_str_funcs  strings.Builder   // auto-generated .str() methods
  // ... more builders
}
```

The final C file is assembled by concatenating these builders:
```
cheaders → typedefs → definitions → out → auto_str_funcs
```

This solves C's forward-declaration problem: types can be defined before they're used.

### Type Mapping

| V Type | C Type |
|--------|--------|
| `int` | `int` |
| `i64` | `int64_t` |
| `f64` | `double` |
| `bool` | `bool` (from stdbool.h) |
| `string` | `string` (V runtime struct) |
| `[]int` | `array` (V runtime struct) |
| `map[string]int` | `map` (V runtime struct) |
| `?int` | `_option` (result struct) |
| `!int` | `_result` (result struct) |
| `struct Foo {...}` | `struct Foo {...}` |
| `enum Color { R G B }` | `enum Color { Color__R, Color__G, Color__B }` |

### Control Flow

V's `if` is an expression (returns a value), so the C backend handles this
with temporary variables:

```v
// V: val := if x > 0 { 1 } else { 0 }
// Generated C:
int val;
if (x > 0) { val = 1; }
else { val = 0; }
```

For loops translate to C for-loops:
```v
// V: for i in 0..10 { println(i) }
// Generated C:
for (int i = 0; i < 10; ++i) { println__xxx(i); }
```

Match statements become switch or if-else chains:
```v
// V: match x { 1 { ... } 2 { ... } else { ... } }
// Generated C:
switch (x) {
  case 1: { /* ... */ break; }
  case 2: { /* ... */ break; }
  default: { /* ... */ break; }
}
```

### Memory Management

V supports multiple memory management strategies, all generating C calls:

```c
// GC mode (default)
__global_allocator = gc_allocator;

// Autofree mode
void* mem = __malloc(nbytes);
// ... use mem ...
__free(mem);

// Arena allocation
__asan_disable(); // for tcc backend
```

### Function Calls

```v
// V: fn add(a int, b int) int { return a + b }
// Generated C:
int add__int_int(int a, int b) {
  return a + b;
}
```

Methods are name-mangled with the receiver type:
```c
// V: fn (s string) len() int
// Generated C:
int string__len(string* s) { return s->len; }
```

### Key Pattern: Section-Based Generation

V generates C code into named sections (builders) that are assembled in a fixed
order. This is a common pattern among C-backends: you can't emit code in
source order because C requires forward declarations for types and functions.

## 3. Haxe / HashLink (Bytecode-to-C)

Haxe compiles to HashLink bytecode, which can then be transpiled to C via
the HL/C backend. This is the closest example to what Astra needs: bytecode-to-C.

### Architecture

```
Source → Haxe Compiler → HL Bytecode → HL/C Transpiler → C Code → cc → Binary
```

The HL/C transpiler lives in the HashLink runtime (`src/`). The key insight:
**each bytecode instruction maps to a C function call or inline C statement.**

### Core Algorithm: Bytecode-to-C Translation

The HashLink C backend works by:

1. **Each function becomes a C function** with a fixed signature
2. **Local variables become local C variables** (the HL stack is represented as C stack frames)
3. **Each bytecode opcode becomes inline C** or a runtime call

The generated C looks like:

```c
// Haxe source:
// function greet(name: String): String {
//   return "Hello, " + name;
// }

// Generated HL/C:
HL_PRIM hlString greet(hlString name) {
  // Stack-based locals as C variables
  hlString _tmp1;
  hlString _tmp2;
  
  // OP_STRING: load constant
  _tmp1 = hl_alloc_string("Hello, ");
  
  // OP_ADD: string concatenation
  _tmp2 = hl_string_append(_tmp1, name);
  
  // OP_RETURN
  return _tmp2;
}
```

### Type Mapping

HashLink defines its own type system that maps to C via `hl.h`:

| HL Type | C Type |
|---------|--------|
| `i32` | `int` |
| `i64` | `int64_t` |
| `f32` | `float` |
| `f64` | `double` |
| `bool` | `bool` |
| `bytes` | `vbyte*` |
| `string` | `hl_string` |
| `array<T>` | `hl_array` |
| `obj` | `hl_obj` (hash-based field access) |
| `enum` | `hl_enum` |

### Control Flow

Bytecode jumps become C gotos or structured control flow:

```
// Bytecode:
// LOOP:
//   ...
//   IF_CMP_GOTO LOOP

// Generated C:
goto LOOP;
LOOP:
  // ... loop body ...
  if (condition) goto LOOP;
```

Some patterns are decompiled back to structured C (for loops, while loops).

### Memory Management

HashLink uses a GC that is linked as a runtime library (`libhl`). The generated
C calls GC primitives:

```c
// Allocation
vdynamic* obj = hl_alloc_obj(type_info);

// GC root registration
hl_add_root(obj);

// GC collection
hl_gc_major();
```

### Function Calls

```c
// Direct call
int result = add(x, y);

// Virtual dispatch (object methods)
vdynamic* result = hl_obj_call(obj, method_name, args);

// Closures
closure = hl_alloc_closure(type, function_ptr, env);
```

### Key Pattern: Stack-to-Stack Translation

HashLink's bytecode is stack-based. The C backend maintains this stack model
by mapping bytecode stack slots to C local variables. Each bytecode instruction
that reads from the stack reads from a named C variable; each instruction that
writes to the stack writes to a named C variable.

The generated C is then **optimized by the C compiler** (gcc/clang), which
performs register allocation, constant folding, etc. This is the fundamental
trick: you get the benefits of C's optimizer for free.

## 4. Crystal (LLVM-based)

Crystal compiles to LLVM IR and uses LLVM's code generation to produce native
code. It does **not** generate C directly, but its approach is relevant for
comparison.

### Architecture

```
Source → Parser → AST → Semantic Analysis → LLVM IR → LLVM Backend → Native Code
```

Crystal's compiler is written in Crystal itself (self-hosting). The code
generation phase lives in `src/compiler/crystal/codegen/`.

### Core Algorithm

Crystal generates LLVM IR using Crystal's LLVM bindings (`src/llvm/`):

```crystal
# Crystal generates LLVM IR like:
# define i64 @add(i64 %a, i64 %b) {
#   %result = add i64 %a, %b
#   ret i64 %result
# }
```

Each Crystal method becomes an LLVM function. Object types become LLVM struct
types. Virtual dispatch uses LLVM's indirect call mechanism.

### Type Mapping

| Crystal Type | LLVM Type | Runtime C Type |
|-------------|-----------|----------------|
| `Int32` | `i32` | `int32_t` |
| `Int64` | `i64` | `int64_t` |
| `Float64` | `double` | `double` |
| `Bool` | `i1` | `bool` |
| `String` | `{i64, ptr}` | struct with len + data |
| `Array(T)` | `{i64, ptr, ptr}` | struct with len + data + GC |
| `Object` | `{vtable_ptr, fields...}` | struct with vtable |

### Key Pattern: LLVM as the Backend

Crystal doesn't generate C; it generates LLVM IR directly. This gives it
access to LLVM's optimizer and all target architectures. The tradeoff is that
Crystal depends on LLVM (a large, complex dependency).

For Astra's bootstrap, a C backend is more appropriate than LLVM because:
1. C compilers are ubiquitous
2. No large dependency
3. The C compiler handles optimization
4. Debugging is easier (readable C output)

## 5. TCC (Tiny C Compiler)

TCC is relevant not because it generates C from bytecode, but because V and
other languages use it as a **fast C compilation backend**.

### Architecture

TCC compiles C source directly to machine code in a single pass, without
an assembler or linker step:

```
C Source → Preprocessor → Parser → IR (vstack) → Native Code (directly)
```

### The vstack: TCC's Internal IR

TCC uses a **value stack** (`vstack`) internally — an array of `SValue`
(structured values) that represents the expression evaluation stack:

```c
typedef struct SValue {
  CType type;      // C type of the value
  int r;           // register/location of the value
  int r2;          // second register (for 64-bit on 32-bit)
  union {          // value content
    int i;
    unsigned int ui;
    double d;
    long double ld;
    // ... more
  } c;
  int sym;         // symbol index
} SValue;
```

### Key Insight for Astra

TCC's `-run` mode compiles and executes C in memory. The internal IR is
very close to C's semantics — it's essentially a typed value stack. This
is conceptually what a bytecode-to-C translator does: map stack operations
to C expressions.

## 6. Go (SSA Backend)

Go's compiler uses SSA (Static Single Assignment) form. While Go compiles
to machine code directly (not C), its SSA design is instructive.

### Architecture

```
Source → AST → Type-checking → SSA IR → Optimizations → Machine Code
```

### SSA Design

Go's SSA uses block parameters (not phi nodes):

```
// Go SSA for: func add(a, b int) int { return a + b }
b1:
  v1 = Parameter mem
  v2 = Const64 <int> 0
  Jump → b2
b2:
  v3 = Phi v1 v4
  v4 = Add64 v2 v3
  Return v4
```

### Key Difference from C-Backends

Go's SSA is designed for register-based targets. To generate C from Go SSA,
you would need to:
1. Convert phi nodes to C variable assignments
2. Convert SSA values to C local variables
3. Convert basic blocks to C labels + gotos (or structured control flow)

The Go team explored C output via gccgo (Go frontend for GCC), which
generates GCC's GIMPLE IR (very close to C) from Go's type-checked AST.

## 7. Cranelift (Register-based IR)

Cranelift is a compiler backend that generates native code. It does NOT
generate C, but its IR design is relevant for comparison.

### Architecture

```
Source → Frontend → CLIF IR → Legalization → VCode → Machine Code
```

### CLIF IR Design

Cranelift IR (CLIF) is SSA-based with block parameters:

```
function %add(i64, i64) -> i64 {
block0(v0: i64, v1: i64):
  v2 = iadd v0, v1
  return v2
}
```

### Key Insight: VCode

Cranelift's new backend uses **VCode** — a virtual-register representation
that maps closely to machine code:

```rust
enum Inst {
  Mov64 { dst: Reg, src: Operand },
  Add64 { dst: Reg, lhs: Reg, rhs: Operand },
  // ...
}
```

### If Cranelift Had a C Backend

To translate Cranelift IR to C:
1. Each SSA value becomes a C local variable: `int64_t v2 = v0 + v1;`
2. Each basic block becomes a C block (possibly with goto/label)
3. Block parameters become assignments at block entry
4. Function calls become C function calls
8. Alloca becomes stack allocation in C

## 8. LuaJIT (Trace Compiler)

LuaJIT is a trace-based JIT compiler. It compiles hot traces (loops) directly
to native machine code using DynASM. It does not generate C, but the trace
compilation model is relevant.

### Architecture

```
Lua Source → Bytecode → Interpreter → Hot Loop Detection → Trace Recording
              → SSA IR → Optimization → DynASM → Native Code
```

### Trace Compilation

LuaJIT records traces as linear sequences of operations:

```
-- Lua code:
local function fact(n)
  local a = 1
  for i = 1, n do a = a * i end
  return a
end

-- LuaJIT bytecode:
0001 KSHORT 1 1    ; a = 1
0002 KSHORT 2 1    ; i = 1
0003 MOV 3 0       ; n
0004 KSHORT 4 1    ; init = 1
0005 FORI 2 => 0008
0006 MULVV 1 1 5   ; a = a * i
0007 FORL 2 => 0006
0008 RET1 1 2
```

### DynASM: Direct Machine Code Generation

DynASM is a "dynamic assembler" — it generates machine code at runtime by
combining pre-encoded instruction templates with runtime values:

```c
// DynASM syntax (embedded in C):
|  mov eax, foo+17
|  mov edx, [eax+esi*2+0x20]
|  add ebx, [ecx+bar(ptr, 9)]
```

This is NOT C generation — it's direct binary code generation. But the
concept is relevant: each trace operation maps to a sequence of machine
instructions.

### Key Insight: Traces Are Linear

Because traces are linear (no branches within a trace), they map naturally
to C code:

```c
// Trace for factorial loop:
for (int i = 1; i <= n; i++) {
  a = a * i;
}
```

## 9. Common Patterns Summary

After surveying these 8 implementations, these are the recurring patterns:

### Pattern 1: Section-Based Generation

**Used by:** Nim, V, Haxe/HashLink

Generate C code into separate sections (headers, typedefs, definitions,
function bodies) that are concatenated in the correct order. This solves
C's requirement for forward declarations.

```c
// Section order in generated output:
#include <header1.h>      // Section: cheaders
#include <header2.h>

typedef struct Foo Foo;    // Section: typedefs
struct Foo { int x; };

// Forward declarations     // Section: definitions
int bar(Foo* f);

// Function bodies          // Section: out
int bar(Foo* f) { return f->x; }
```

### Pattern 2: AST-to-C Direct Translation

**Used by:** Nim, V

Walk the typed AST and emit C code directly. No intermediate bytecode.
Each AST node type has a corresponding C generation function.

```c
// Nim/V style: each node kind has a handler
case NK_IF:
  emit("if (");
  genExpr(node.condition);
  emit(") ");
  genStmt(node.body);
  if (node.elseBody) {
    emit(" else ");
    genStmt(node.elseBody);
  }
```

### Pattern 3: Stack-to-Variables Translation

**Used by:** Haxe/HashLink

Map bytecode stack slots to C local variables. Each bytecode instruction
reads/writes named C variables instead of a stack.

```c
// Bytecode: PUSH 5; PUSH 3; ADD; STORE x
// Becomes:
int tmp1 = 5;
int tmp2 = 3;
int tmp3 = tmp1 + tmp2;
int x = tmp3;
```

### Pattern 4: Name Mangling for C Compatibility

**Used by:** All

Every language mangles names to avoid C keyword conflicts and to handle
overloading/generics:

```c
// Nim:    add__int_int(int a, int b)
// V:      add__int_int(int a, int b)
// HL/C:   hl_add(hl_int a, hl_int b)
```

Common mangling patterns:
- `__` separator for module/function
- `_T_` for generic type parameters
- `_` prefix for reserved words
- Module path in name for namespacing

### Pattern 5: Runtime Library as C Code

**Used by:** Nim, V, Haxe/HashLink

The language runtime (GC, string operations, I/O) is implemented in C and
linked with the generated code. The generated C calls runtime functions.

```c
// Generated code calls runtime:
string s = string_new("hello");
int len = string_len(s);
array_t arr = array_new(sizeof(int), 10);
gc_collect();
```

### Pattern 6: Type Mapping Table

**Used by:** All

A centralized mapping from source-language types to C types:

| Pattern | Source | C |
|---------|--------|---|
| Fixed-size integers | `i32`, `u64` | `int32_t`, `uint64_t` |
| Platform integers | `int` | `NI` or `intptr_t` |
| Floats | `f32`, `f64` | `float`, `double` |
| Booleans | `bool` | `bool` or `int` |
| Strings | `string` | Struct `{ len, data }` |
| Arrays | `[]T` | Struct `{ len, cap, data }` |
| Options/Results | `?T`, `!T` | Tagged union struct |
| Objects | `class Foo` | Struct with vtable pointer |
| Enums | `enum Color` | `int` or C enum |
| Pointers | `*T` | `T*` |
| Function pointers | `fn(A) -> B` | `ret_type (*name)(arg_type)` |

### Pattern 7: Control Flow Mapping

| Source Construct | Generated C |
|-----------------|-------------|
| `if cond then ... else ...` | `if (cond) { ... } else { ... }` |
| `while cond do ...` | `while (cond) { ... }` |
| `for i in range ...` | `for (type i = start; i < end; i++) { ... }` |
| `match x { cases }` | `switch (x) { case ...: ... }` or `if-else` |
| `return expr` | `return expr;` |
| `break` | `break;` |
| `continue` | `continue;` or `goto Lcontinue;` |
| `block { ... }` | `{ ... }` (scoped block) |
| Exception/try | `setjmp`/`longjmp` or platform-specific |

### Pattern 8: Memory Management via Runtime Calls

| Strategy | Generated C |
|----------|-------------|
| Boehm GC | `GC_malloc(n)`, `GC_free(p)` |
| Reference counting | ` incref(p); decref(p);` |
| Manual | `malloc(n)`, `free(p)` |
| Arena | `arena_alloc(a, n)`, `arena_free(a)` |
| ARC/ORC | `nimIncRef(p); nimDecRef(p);` |
| Hybrid | Select per type (stack vs heap) |

### Pattern 9: Function Call Conventions

```c
// Regular function
ReturnType func_name(ArgType1 arg1, ArgType2 arg2) { ... }

// Method (receiver as first parameter)
ReturnType type_name__method_name(type* self, ArgType arg) { ... }

// Generic (specialized per type)
ReturnType func_name__TypeA(TypeA arg) { ... }
ReturnType func_name__TypeB(TypeB arg) { ... }

// Closure (function pointer + environment struct)
struct closure_env { CapturedType cap1; ... };
ReturnType invoke_closure(closure_env* env, ArgType arg) { ... }
```

### Pattern 10: Generated C Boilerplate

Every C backend generates a similar preamble:

```c
// Generated by [Language] compiler
// Do not edit manually

#include <stdint.h>
#include <stdbool.h>
#include <stdlib.h>
#include <string.h>
#include <stdio.h>

// Forward declarations
typedef struct LanguageRuntime LanguageRuntime;
typedef struct GCState GCState;

// Runtime type info
typedef struct TypeInfo { ... } TypeInfo;

// ... type definitions ...
// ... forward declarations ...
// ... function implementations ...
// ... main function ...
```

## 10. Implications for Astra

Based on this survey, here are concrete recommendations for Astra's C backend:

### Recommended Architecture

```
Astra Source → Lexer → Parser → AST → Type Checker → Typed AST
    → Bytecode Emitter → Bytecode → C Code Generator → C Source → cc → Binary
```

The bytecode-to-C approach (like Haxe/HashLink) is ideal for Astra because:
1. The seed compiler already has a bytecode emitter and VM
2. A C backend can reuse the bytecode format
3. The generated C is "just another target" for the same bytecode
4. Debugging: you can inspect the C output

### Core Data Structure

```c
typedef struct CGenState {
  FILE* out;              // main output file
  FILE* headers;          // forward declarations
  FILE* types;            // type definitions
  int tmp_counter;        // unique temp variable counter
  int label_counter;      // unique label counter
  TypeMap* type_map;      // Astra type → C type mapping
  StringTable* strings;   // string literal table
} CGenState;
```

### Key Translation Rules (Proposed)

1. **Each bytecode function → one C function**
2. **Each stack slot → one C local variable**
3. **Each opcode → inline C expression/statement**
4. **Strings → `{ char* data; int len; }` struct**
5. **Arrays → `{ void* data; int len; int cap; }` struct**
6. **Objects → C structs with vtable pointer**
7. **GC → runtime library calls** (initially `malloc`/`free`, later Boehm GC)
8. **Control flow → structured C** (if/while/for), falling back to goto for
   complex patterns
9. **Function calls → C function calls** with name mangling
10. **The C compiler handles optimization** (register allocation, constant
    folding, dead code elimination)
